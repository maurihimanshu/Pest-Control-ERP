# Skill: Service Visit Domain

## Purpose
To track the granular, physical execution of a job on-site by a technician. This is the lowest level of the operational hierarchy.

## When to Use / When NOT to Use
**Use When:** Tracking GPS check-ins, task checklists, material usage, before/after photos, and customer signatures.
**NOT to Use:** For scheduling or high-level dispatch (use Work Order).

## Required Context
The Service Visit is heavily tied to the Technician Mobile App, which operates offline-first. Data arriving at the backend might be delayed.

## Domain Rules & Constraints
1. **Offline Sync Support:** Endpoints must accept timestamps generated by the device, not just rely on `now()`, to accurately reflect when actions occurred while offline.
2. **Evidence Capture:** Store URIs to Object Storage for photos and signatures. Do not store binary data in the database.
3. **Material Usage:** Data captured here (chemicals used) must transactionally trigger inventory deductions upon synchronization.

## Entity Structure
*   `id` UUID
*   `work_order_id` UUID (FK)
*   `employee_id` UUID (FK)
*   `arrival_time` TIMESTAMP WITH TIME ZONE
*   `start_time` TIMESTAMP
*   `end_time` TIMESTAMP
*   `checklist` JSONB (Dynamic tasks completed)
*   `materials_used` JSONB (List of product_ids and quantities)
*   `before_photos` TEXT[] (URIs)
*   `after_photos` TEXT[] (URIs)
*   `gps_lat` DECIMAL, `gps_lng` DECIMAL
*   `signature_url` TEXT
*   `notes` TEXT
*   `status` VARCHAR (SCHEDULED, IN_PROGRESS, COMPLETED, INCOMPLETE)

## Spring Service Methods
*   `ServiceVisit logArrival(UUID visitId, GpsLocation loc, LocalDateTime clientTime)`
*   `ServiceVisit completeVisit(UUID visitId, VisitCompletionDto data)`
*   `void syncOfflineVisits(List<VisitSyncDto> offlineData)`

## API Endpoints
*   `POST /api/v1/dispatch/visits/{id}/arrive`
*   `POST /api/v1/dispatch/visits/{id}/complete`
*   `POST /api/v1/dispatch/visits/sync` (Batch offline sync)

## Database Considerations
*   JSONB is critical here for the flexible `checklist` and `materials_used` arrays.
*   Expect bursts of writes when a technician regains network connectivity.

## RabbitMQ Events
*   `ServiceVisitCompletedEvent` -> Triggers Work Order status evaluation and Inventory deduction process.

## Validation Checklist
- [ ] Does it handle delayed synchronization gracefully?
- [ ] Are photo URLs properly referenced and verified against storage?
- [ ] Is inventory deducted transactionally when a visit completes?

## Common Mistakes
*   Using server time for arrival/completion instead of device time for offline events.
*   Failing to handle conflict resolution if a visit is updated from two devices simultaneously.
