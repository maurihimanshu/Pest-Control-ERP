# Skill: Service Visit Domain

## Purpose
To track the granular, physical execution of a job on-site by a technician. This is the lowest level of the operational hierarchy.

## When to Use / When NOT to Use
**Use When:** Tracking GPS check-ins, task checklists, material usage, before/after photos, and customer signatures.
**NOT to Use:** For scheduling or high-level dispatch (use Work Order).

## Required Context
The Service Visit is heavily tied to the Technician Mobile App, which operates offline-first. Data arriving at the backend might be delayed.

## Domain Rules & Constraints
1. **Offline Sync Support:** Endpoints must accept timestamps generated by the device (`client_created_at`), not just rely on `now()`, to accurately reflect when actions occurred while offline.
2. **Cryptographic Payload Signing (P0-02):** High-risk field operations (`START_VISIT`, `COMPLETE_VISIT`, `LOG_CHEMICALS`) MUST be cryptographically signed by the device's hardware-backed Android Keystore EC P-256 private key and verified server-side (`X-Device-Signature`) before executing database state changes.
3. **Evidence Capture & Media Lifecycle:** Store URIs to Object Storage for photos and signatures (`LOCAL_CAPTURE → ... → ATTACHED`). Do not store raw binary blobs in PostgreSQL.
4. **Material Usage & Inventory Deduction:** Chemical usage logged during visit completion MUST execute inventory deduction transactionally via `InventoryStockService` inside the PostgreSQL visit completion transaction with `SELECT ... FOR UPDATE` on `chemical_batches`.
5. **Canonical Lifecycle:** `SCHEDULED` -> `ON_THE_WAY` -> `ARRIVED` -> `STARTED` -> `COMPLETED` (or `FAILED` | `CANCELLED`).

## Entity Structure
*   `id` UUID
*   `work_order_id` UUID (FK)
*   `primary_employee_id` UUID (FK)
*   `status` VARCHAR (`CHECK (status IN ('SCHEDULED', 'ON_THE_WAY', 'ARRIVED', 'STARTED', 'COMPLETED', 'CANCELLED', 'FAILED'))`)
*   `scheduled_start_time` TIMESTAMP WITH TIME ZONE
*   `actual_arrival_time` TIMESTAMP WITH TIME ZONE
*   `actual_start_time` TIMESTAMP WITH TIME ZONE
*   `actual_completion_time` TIMESTAMP WITH TIME ZONE
*   `arrival_latitude` NUMERIC(10, 8), `arrival_longitude` NUMERIC(11, 8)
*   `customer_signature_url` VARCHAR(500)
*   `technician_notes` TEXT
*   `created_at`, `updated_at`

## Spring Service Methods
*   `ServiceVisit logArrival(UUID agencyId, UUID visitId, GpsLocation loc, Instant clientTime)`
*   `ServiceVisit startVisit(UUID agencyId, UUID visitId, Instant clientTime)`
*   `ServiceVisit completeVisit(UUID agencyId, UUID visitId, VisitCompletionDto data, byte[] deviceSignature)`
*   `SyncResult syncOfflineVisits(UUID agencyId, UUID deviceId, List<OfflineOperationDto> operations)`

## API Endpoints
*   `POST /api/v1/dispatch/visits/{id}/arrive`
*   `POST /api/v1/dispatch/visits/{id}/start`
*   `POST /api/v1/dispatch/visits/{id}/complete`
*   `POST /api/v1/dispatch/visits/sync` (Batch offline sync)

## Database Considerations
*   Check constraints enforce status enum.
*   Inventory batch row locks (`chk_batch_qty_nonneg`) prevent negative chemical inventory.

## RabbitMQ Events (Published via Transactional Outbox)
*   `ServiceVisitCompleted` -> Triggers Work Order status evaluation, invoice preparation, downstream notifications, and post-commit low stock checks (Note: Inventory deduction is executed strictly within the PostgreSQL visit completion transaction, NOT via RabbitMQ).

## Validation Checklist
- [ ] Is the cryptographic Keystore signature (`X-Device-Signature`) verified for high-risk operations?
- [ ] Does it handle delayed synchronization and sequence ordering gracefully?
- [ ] Are photo URLs verified against object storage?
- [ ] Is inventory deducted transactionally in the same PostgreSQL transaction when a visit completes?

## Common Mistakes
*   Relying on server clock for arrival/completion instead of device timestamp for offline events.
*   Allowing unsigned offline completions.
